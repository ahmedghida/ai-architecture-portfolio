# Governance Pack: Marketing Automation with AI & Agents

Property marketplace (Property Finder-style), seeker side, WhatsApp channel · Prepared by Ahmed

## 1. System and assumptions

AI agents send property seekers (buyers) personalized WhatsApp messages: new matching listings, price-increase alerts on saved properties, and re-engagement. A Matching Engine (vector search plus fixed rules, no LLM) selects listings; a Content Agent (LLM) fills pre-approved message templates. Assumptions: about 100-500K active listings, about 2,000 LLM calls per day (cost scales with listings, not users), Arabic and English, a small team, PostgreSQL as the main database. ## 2. Architecture principles

| # | Principle | Business goal | Where it shows up |
| --- | --- | --- | --- |
| P1 | Facts come from the source of truth: prices, specs and promises are never generated by the LLM and are re-checked at send time | Seeker trust in listings; avoid legal and reputational liability | Claim Verifier; ADR-001, ADR-003 |
| P2 | Human oversight scales with risk: routine messages pass automatically; new templates and price-increase messages need approval | Protect the brand without slowing campaigns | Approval Queue; ADR-003 |
| P3 | Privacy by design (PDPL): consent before any message, minimum data, no buyer data sent to the LLM | Compliance and seeker trust | Consent check; ADR-001 |
| P4 | Measured quality, bounded cost: no release without evals; budget caps and monitoring | Consistent quality and predictable spend | LLM Gateway; ADR-001, 002, 003 |

## 4. ARB checklist

The ARB (security, privacy/legal, product, tech lead) reviews: a new model or LLM vendor, a new channel, a new data type, any consent or PDPL change, a new ADR, and any fine-tuning or training of the CLV, segmentation or churn models. Other changes go through the automated guardrail only.

**Security**

- ☐ API keys live only in the LLM Gateway
- ☐ Listing text is treated as untrusted input (prompt injection tested)
- ☐ Agents have least-privilege, read-only access to listings
- ☐ Every generated message and approval is logged

**Privacy (PDPL)**

- ☐ Consent is recorded per channel before any send; opt-out is honored
- ☐ Prompts contain no buyer data
- ☐ Data is minimized and retention is defined
- ☐ Training data for CLV, segmentation and churn models is covered by consent, and models are tested for discriminatory segments
- ☐ Legal has confirmed any cross-border data transfer

**Evals**

- ☐ Golden set of Arabic and English messages
- ☐ Prices and specs match the Listings DB in 100% of test cases
- ☐ No pressure or misleading wording
- ☐ Regression eval passes before every prompt or model change
- ☐ Claim Verifier tested with injected wrong prices

**Cost**

- ☐ Daily budget cap and alert in the LLM Gateway
- ☐ Cost per message is tracked
- ☐ Fallback provider has its own cap

**Human oversight**

- ☐ New templates are approved before use
- ☐ Frequency cap per seeker
- ☐ Kill switch pauses all sends
- ☐ Overrides are logged with a reason

## 5. Automated guardrail

Two layers run on every pull request. (1) CI check (form): the PR must link an ADR and a completed checklist and pass the eval suite, otherwise it cannot merge. (2) Design-review agent (content): an LLM reads the design doc or diff, compares it with P1-P4, and cites the principle and the exact line. It blocks the merge on P1 or P3 violations and only comments on P2 or P4. An ARB member can override with a recorded reason, since the agent itself can be wrong.
